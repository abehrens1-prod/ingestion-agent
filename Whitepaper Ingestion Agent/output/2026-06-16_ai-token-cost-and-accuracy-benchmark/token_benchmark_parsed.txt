[LIST] Token Cost and Wrong Answers in AI-Driven Analytics
[P] The dominant pattern for AI analytics today is text-to-SQL: the AI model receives raw schema
[P] information, generates a SQL query, and executes it against the database. Sequeda et al.
[P] (2023) establish text-to-SQL as the standard deployment baseline, and it is widely used in
[P] production environments today. It has two distinct failure modes that become more costly at
[P] scale.
[P] 1.1 Token Cost
[P] Every text-to-SQL query requires the AI model to first receive the full schema: table names,
[P] column names, data types, and foreign key relationships. For a 28-table schema this adds
[BOLD] approximately 4,428 tokens of schema context per query . For production enterprise schemas
[P] with 100–500+ tables, this grows to 100,000+ tokens per query.
[P] At current LLM pricing of $3.00 per million input tokens, a ten-person analytics team running
[P] 200 queries per day against a 200-table schema incurs over $15,000/month in schema
[P] context overhead alone, before any SQL query is executed against the data. This cost is paid
[P] fresh on every query; schema context is not cached across stateless LLM calls.

[P] 1.2 Wrong Answers from Complex Queries
[P] When an AI model generates SQL against a raw schema, it must independently reason about
[P] join paths, bridge tables, and aggregation grain. That business logic is entirely absent from the
[P] schema definitions. For simple single-table queries this works. For queries spanning multiple
[P] fact tables, the model frequently selects the wrong join path and returns numbers that are
[P] materially wrong but structurally valid.
[LIST] There is no error, no warning, and no way for the user to know the answer is
[LIST] wrong without already knowing the correct answer.
[P] In this benchmark, two multi-fact-table questions returned results from PostgreSQL that were
[P] 5–10× inflated or attributed to the wrong policy. Neither failure triggered a SQL error. Both
[P] results would have passed routine review by an analyst who did not already know the correct
[P] answer.

[P] 1.3 Join Complexity and Business Logic
[P] Analytical schemas in real enterprises are layered: star schemas, snowflake schemas, ACORD
[P] insurance models, Kimball dimensional designs, all involving multiple fact tables joined through
[P] carefully chosen bridge tables. The correct join path is not derivable from column names alone;
[P] it is encoded in business rules.
[P] Text-to-SQL generation requires the AI to infer those business rules from table names on every
[P] query. The wider the schema, the more plausible join paths exist, and the more likely the AI
[P] selects the wrong one.

[P] Root Cause
[P] policy_coverage_detail contains one row per policy per coverage year. A 5-year policy
[P] produces 5 PCD rows. When the AI joins policy_amount (fact table) to claim_amount (fact table)
[P] through this shared key, each claim row joins to all 5 coverage year rows, multiplying claim
[P] amounts by 5 before SUM() aggregates. The query shape (one output row per policy) looks
[P] correct. The inflation is invisible without prior knowledge of the correct answer.
[P] Why Mosaic Is Correct
[P] The semantic model isolates fact tables. Coverage and claim metrics are computed via
[P] independent canonical paths and combined only as pre-aggregated results at the policy grain.
[P] The multiplicative error cannot form.

[LIST] Schema-invariant cost: A 500-table enterprise schema costs exactly the same as a 28-

[LIST] many people are asking.

[LIST] produce a wrong join because it never writes a join. The Mosaic MCP produces
[LIST] deterministic, semantically-validated queries every time.

[LIST] Conclusion
[P] Connecting AI agents directly to raw databases is not merely expensive; it is structurally
[P] unreliable for the complex multi-table queries that drive enterprise analytics decisions.
[P] Mosaic’s semantic layer addresses both dimensions simultaneously. By encoding business logic
[P] (canonical join paths, fan-out protections, party-identity unification) once in the semantic
[P] model, every subsequent query inherits those guarantees regardless of which AI model,
[P] analyst, or interface issues it. The accuracy improvement is not a tuning artifact; it is a
[P] structural property of the architecture.
[P] The cost savings are equally structural. Mosaic MCP reduces schema context overhead by
[P] 53% and SQL complexity by 24%, delivering 37% cost reduction in the benchmark and 50–70%
[P] at production scale with caching. Strategy AI Agents remove the AI from the query execution
[P] path entirely, achieving 95–98% cost reduction regardless of schema complexity, an
[P] architecture that makes AI query costs effectively schema-invariant and user-count-invariant.
[P] For organizations evaluating AI analytics infrastructure, the question is no longer whether to
[P] use a semantic layer. The benchmark data demonstrates its necessity for accurate results on
[P] multi-fact-table queries.
